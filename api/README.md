# Implement this API

#### In this assessment you will be tasked with filling out the functionality of different methods that will be listed further down.

These methods will require some level of API interactions with Mock Employee API at http://localhost:8112/api/v1/employee.

Please keep the following in mind when doing this assessment:
* clean coding practices
* test driven development
* logging
* scalability

### Endpoints to implement

_See `com.reliaquest.api.controller.IEmployeeController` for details._

getAllEmployees()

    output - list of employees
    description - this should return all employees

getEmployeesByNameSearch(...)

    path input - name fragment
    output - list of employees
    description - this should return all employees whose name contains or matches the string input provided

getEmployeeById(...)

    path input - employee ID
    output - employee
    description - this should return a single employee

getHighestSalaryOfEmployees()

    output - integer of the highest salary
    description - this should return a single integer indicating the highest salary of amongst all employees

getTop10HighestEarningEmployeeNames()

    output - list of employees
    description - this should return a list of the top 10 employees based off of their salaries

createEmployee(...)

    body input - attributes necessary to create an employee
    output - employee
    description - this should return a single employee, if created, otherwise error

deleteEmployeeById(...)

    path input - employee ID
    output - name of the employee
    description - this should delete the employee with specified id given, otherwise error

## Post Completion Notes

The implementation of all required endpoints is complete, tested, and
integrated with the Mock Employee API. Key concerns such as clean code practices,
logging, caching, exception handling, and fault tolerance have been addressed in the design.

### Design Decisions

#### 1. Separation of Concerns
The application is organized using controller, service, and model layers, promoting modularity, testability, and scalability.

#### 2. Use of `RestTemplate` for Standard CRUD
`RestTemplate` is used for most GET and POST operations due to its simplicity and ease of use with synchronous HTTP calls.

#### 3. Use of `WebClient` for DELETE with Request Body
The mock API requires a **DELETE** request that includes a **request body** — something not supported by `RestTemplate` out of the box.
To accommodate this, `WebClient` (from Spring WebFlux) is used for the `deleteEmployeeById()` operation, enabling full control over HTTP method, URI, headers, and body.

#### 4. API Response Wrapping
All responses from the mock API follow a standard format: `{ "data": ..., "status": ... }`. To handle this generically, `ParameterizedTypeReference` is used with `RestTemplate` to deserialize responses properly.

#### 5. Caching
Spring Cache (`@Cacheable`, `@CacheEvict`) is applied to methods like `getAllEmployees()` and `getEmployeeById()` to avoid unnecessary remote API calls and improve response time.

#### 6. Fault Tolerance via Resilience4j
Resilience4j annotations (`@Retry`, `@CircuitBreaker`) are added to critical external calls (e.g., delete and create operations) to improve reliability and gracefully handle rate-limiting or transient failures.

#### 7. Logging
Structured logging is used consistently to trace request flows, errors, and debug information throughout the service layer.

#### 8. Exception Handling
Custom exceptions (e.g., `EmployeeServiceException`, `EmployeeNotFoundException`) provide clear error feedback and separate internal failures from client-facing API behavior.

### Assumptions

#### 1. Deletion by Name
Since the mock API's DELETE endpoint accepts `name` in the request body and URL path, the application first retrieves the employee by ID to get the required name for deletion.

#### 2. Email Field
The email is not part of the `createEmployee` request. It is auto-generated by the mock server upon creation and returned in the response.

#### 3. Circuit Breaker Recovery
If the circuit breaker trips or retry fails, fallback methods provide controlled exceptions rather than raw errors, to preserve API stability.
